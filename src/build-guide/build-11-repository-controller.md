<div class="level overview">

The last chapter of Phase 2 connects the database to HTTP. Two pieces
remain between a request and the DAO:

- `ScholenRepository` / `ScholenRepositoryImpl`: the layer controllers talk to. It extends Spring Data's `Repository` marker interface, but its implementation is written by hand and simply delegates to `ScholenDao`.
- `SchoolController` / `v1/ScholenController`: an interface whose `default` methods hold the endpoints, and a thin class that gives them a URL and a repository.

At the end of this chapter, the Swagger UI's `v1` group lists four
school endpoints, `GET /api/v1/school` returns the four schools from
MariaDB, and a `POST` adds a fifth one through the `to_write` login.
`HelloController` has done its job and is deleted.

**After this chapter you can:**

- explain why the VWO's repositories extend Spring Data's `Repository` yet are implemented by hand, and what `@NoRepositoryBean` prevents;
- write endpoints as `default` methods in an interface and expose them from a versioned controller;
- return `ResponseEntity` with the right status, and turn an `Optional` into a 200 or a 404;
- predict a bean's name and avoid name clashes between controllers.

### Why a repository on top of the DAO

At first sight `ScholenRepositoryImpl` adds nothing: every method is one
line that calls the DAO. Its value is in the boundary it draws. The
controller depends on an interface phrased in terms of the API
(`findById`, `save`), while the DAO is phrased in terms of Hibernate
(`getOptional`, `saveOrUpdate`, `addAll`). When an endpoint needs data
from two tables, the repository combines two DAOs: the VWO's
`ScholenRepositoryImpl` takes a `ScholenDao` and a `ScholenFacturatieDao`,
and `updateInvoiceData` uses both. In chapter 16 one repository method
will drive several DAOs inside a single transaction.

### Spring Data's Repository, without Spring Data

`ScholenRepository` reads:

```java
@NoRepositoryBean
public interface ScholenRepository extends Repository<Scholen, Short> {
```

`org.springframework.data.repository.Repository<T, ID>` is the root
interface of Spring Data. It declares no methods. In a typical Spring
Data JPA project, you write an interface that extends it and Spring
*generates* the implementation at startup: `findAll()`, `findById(id)`
and `save(entity)` come for free, and `findByGemeente(String)` becomes a
query because of its name. EF Core has no direct counterpart; it is as
if a `DbSet` could grow methods from their names.

The VWO uses the marker and the vocabulary (`findAll`, `findById`,
`save`, `saveAll`, `existsById` are Spring Data's method names), but none
of the generation. Two things keep Spring Data from generating anything
here:

1. Spring Boot's Spring Data JPA auto-configuration only runs when there
   is a `DataSource` bean, and [chapter 8](build-08-hibernate-xml.md)
   made sure there is none. So nothing scans for repository interfaces.
2. `@NoRepositoryBean` says "never generate an implementation for this
   interface", in case scanning is ever switched on. Spring Data made the
   annotation for intermediate interfaces that only exist to be
   extended; the VWO puts it on every repository interface as a guard.

The implementation is written by hand and annotated `@Repository`, so
component scanning registers it like any other bean. Hand-written
implementations also explain one VWO oddity worth knowing:

```java
@Override
public List<Scholen> saveAll(Iterable<Scholen> iterable) {
    return null;
}
```

The VWO's v1 `POST /school` calls exactly this method, so it saves
nothing and answers 200 with an empty body. In the VWO's interface the
endpoint is marked `@Deprecated` and `@Hidden` (hidden from Swagger).
TechOlympiad implements `saveAll` and shows the endpoint.

### Constructor injection

```java
private final ScholenDao scholenDao;

@Autowired
public ScholenRepositoryImpl(ScholenDao scholenDao) {
    this.scholenDao = scholenDao;
}
```

This is ordinary constructor injection, the style .NET uses everywhere.
Spring finds the constructor, resolves a `ScholenDao` (there is exactly
one bean of that type: the proxy of `ScholenDaoImpl`), and passes it in.
Since Spring 4.3 a class with a single constructor does not need
`@Autowired` on it; the VWO writes it anyway, and so do we. The field is
`final`, so the dependency can never be missing or replaced, and the
class can be constructed in a test with a plain `new`.

Field injection (`@Autowired private ScholenDao scholenDao;`) also exists
and appears in older Spring code. It hides the dependencies and needs
reflection to set the field. The DAOs' `@Autowired` setters of chapter 10
are the third form, setter injection, which the VWO uses where the
dependency is set in a base class.

### Bean names

Every bean has a name. For a scanned class without an explicit name, it
is the simple class name with a lowercase first letter:

<div class="table-wrap">

| Class | Bean name |
|---|---|
| `ScholenDaoImpl` | `scholenDaoImpl` |
| `ScholenRepositoryImpl` | `scholenRepositoryImpl` |
| `v1.ScholenController` | `scholenController` |
| XML `<bean id="toR">` | `toR` |

</div>

The package is not part of the name. Two scanned classes with the same
simple name in different packages, say `v1.FunctionController` and
`v2.FunctionController`, both want the name `functionController`, and
the application refuses to start with
`ConflictingBeanDefinitionException: Annotation-specified bean name
'functionController' for bean class [...v2.FunctionController] conflicts
with existing, non-compatible bean definition of same name and class
[...v1.FunctionController]`.
`spring.main.allow-bean-definition-overriding=true` does not help here:
that setting is about definitions registered over one another, and the
scanner checks for this conflict on its own.

The VWO avoids the clash in two ways. Usually it names the bean
explicitly: `@RestController("functionController.v1")`. For schools it
picked different class names: `v1.ScholenController` and
`v2.SchoolController`, which become `scholenController` and
`schoolController`. The interface `SchoolController` is not a bean at
all, so its name collides with nothing.

### Endpoints as default methods

Since Java 8, an interface method can have a body if it is marked
`default`. A class that implements the interface inherits the method as
if it had written it. `SchoolController` uses that to hold the
endpoints:

<div class="code-walk" data-code-walk>

```java
public interface SchoolController {

    ScholenRepository getRepository();                                   // (1)

    @GetMapping("/{schoolId}")                                           // (2)
    @Operation(summary = "Get school information by school ID")          // (3)
    default ResponseEntity<Scholen> getById(@PathVariable("schoolId") Short schoolId) { // (4)
        return getRepository().findById(schoolId)                        // (5)
                .map(school -> ResponseEntity.ok().body(school))
                .orElse(ResponseEntity.notFound().build());
    }
```

1. The one abstract method. A default method cannot reach fields of the implementing class, so the interface asks for the repository through a getter, which each controller provides.
2. Spring MVC collects request mappings from the methods of each controller class, including methods inherited from interfaces, and reads their annotations there. The path is relative: the class adds `/api/v1/school`.
3. Swagger's summary line for the operation. springdoc reads it from the same method.
4. Parameter annotations on interface methods are honoured too. The explicit name `"schoolId"` binds the path variable without relying on compiled parameter names (see chapter 10).
5. `findById(short id)` takes a primitive: the `Short` is unboxed. A path variable is required, so it is never `null` here.

</div>

The payoff comes in [chapter 19](roadmap.md): a `v2` controller
implements the same interface under `/api/v2`, and every endpoint exists
in both versions without a line of duplication. C# 8 also has default
interface methods, with a difference: in C#, a default member is only
callable through the interface type, while in Java it becomes a regular
member of the implementing class, which is what lets Spring MVC treat it
as a handler method of the controller.

On the class side, Lombok writes the getter the interface asks for:

```java
@Getter(onMethod_ = {@Override})
private final ScholenRepository repository;
```

`@Getter` on a field generates `public ScholenRepository getRepository()`.
`onMethod_` lists annotations to put on that generated method, here
`@Override`, so the compiler confirms it implements the interface
method. The trailing underscore is Lombok's syntax for this option on
current Java versions.

The VWO puts `@ResponseBody` on several interface methods.
`@RestController` already implies `@ResponseBody` for every handler of
the class, inherited ones included, so we leave it out.

### ResponseEntity and Optional

A handler can return the body directly, as `findAll()` does: Spring
answers 200 and serialises the list. To choose the status, it returns a
<dfn data-def="Spring's HTTP response value: status, headers and body. The counterpart of ASP.NET Core's ActionResult&lt;T&gt;.">ResponseEntity</dfn>,
the counterpart of `ActionResult<T>`:

<div class="table-wrap">

| Spring | ASP.NET Core |
|---|---|
| `ResponseEntity.ok().body(school)` | `Ok(school)` |
| `ResponseEntity.notFound().build()` | `NotFound()` |
| `ResponseEntity.status(HttpStatus.CREATED).body(x)` | `StatusCode(201, x)` / `Created(...)` |

</div>

`findById` returns an `Optional<Scholen>`: a box that holds a school or
nothing, and is never `null` itself. Where C# would return `Scholen?`
and test for `null`, Java chains on the box:
`map(...)` transforms the content if there is one, and
`orElse(...)` supplies the result for an empty box. The result is one
expression: 200 with the school, or 404 without a body.

`POST` answers 200 with the saved list, as in the VWO. A strict REST
API would answer 201 Created; chapter 18 revisits status codes.

### What POST and PUT do in the database

<div class="param-table" data-param-table>

| Endpoint | Type | Description |
|---|---|---|
| `GET /school` | `School[]` | All schools, through `to_read` |
| `GET /school/{schoolId}` | `School?` | One school, or 404. `schoolId` is a `Short` |
| `POST /school` body | `School[]` | New schools with their ids; each one is an `INSERT` through `to_write` |
| `PUT /school` body | `School` | Updates the school with that id, or inserts it when the id is new |

</div>

`POST` calls `saveAll`, which calls `session.save` for each school
inside one `transactionToRW` transaction. Hibernate sends the `INSERT`s
when the transaction commits, all or nothing. An id that already exists
makes the commit fail with
`Duplicate entry '1' for key 'PRIMARY'`, and the response is a 500 until
[chapter 18](build-18-error-handling.md) maps it to a 409.

`PUT` calls `save`, which calls `session.saveOrUpdate`. The id of a
school is assigned by the client, so Hibernate cannot tell from the
object whether the row exists. It first selects the row by id, then
sends an `UPDATE` if it found one and an `INSERT` otherwise. Our `PUT`
is therefore an upsert. Every column is written, so a field left out of
the JSON is stored as `NULL`.

</div>

### The repository

`src/main/java/be/techolympiad/common/restAPI/repositories/ScholenRepository.java`:

```java
package be.techolympiad.common.restAPI.repositories;

import be.techolympiad.common.dbEntities.Scholen;
import org.springframework.data.repository.NoRepositoryBean;
import org.springframework.data.repository.Repository;

import java.util.List;
import java.util.Optional;

@NoRepositoryBean
public interface ScholenRepository extends Repository<Scholen, Short> {

    List<Scholen> findAll();

    Optional<Scholen> findById(short id);

    Scholen save(Scholen s);

    List<Scholen> saveAll(Iterable<Scholen> iterable);

}
```

`src/main/java/be/techolympiad/common/restAPI/repositories/ScholenRepositoryImpl.java`:

```java
package be.techolympiad.common.restAPI.repositories;

import be.techolympiad.common.dao.ScholenDao;
import be.techolympiad.common.dbEntities.Scholen;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Repository;

import java.util.List;
import java.util.Optional;

@Repository
public class ScholenRepositoryImpl implements ScholenRepository {

    private final ScholenDao scholenDao;

    @Autowired
    public ScholenRepositoryImpl(ScholenDao scholenDao) {
        this.scholenDao = scholenDao;
    }

    @Override
    public List<Scholen> findAll() {
        return scholenDao.findAll();
    }

    @Override
    public Optional<Scholen> findById(short id) {
        return scholenDao.getOptional(id);
    }

    @Override
    public Scholen save(Scholen s) {
        return scholenDao.saveOrUpdate(s);
    }

    @Override
    public List<Scholen> saveAll(Iterable<Scholen> iterable) {
        return scholenDao.saveAll(iterable);
    }

}
```

Two annotations named `Repository` meet in this package: Spring Data's
interface `org.springframework.data.repository.Repository` and Spring's
stereotype `org.springframework.stereotype.Repository`. Check the
imports: the interface file needs the first, the class the second.

### The controller interface

`src/main/java/be/techolympiad/common/restAPI/controllers/SchoolController.java`:

```java
package be.techolympiad.common.restAPI.controllers;

import be.techolympiad.common.dbEntities.Scholen;
import be.techolympiad.common.restAPI.repositories.ScholenRepository;
import io.swagger.v3.oas.annotations.Operation;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.PutMapping;
import org.springframework.web.bind.annotation.RequestBody;

import java.util.List;

public interface SchoolController {

    ScholenRepository getRepository();

    @GetMapping
    @Operation(summary = "Get all schools")
    default List<Scholen> findAll() {
        return getRepository().findAll();
    }

    @GetMapping("/{schoolId}")
    @Operation(summary = "Get school information by school ID")
    default ResponseEntity<Scholen> getById(@PathVariable("schoolId") Short schoolId) {
        return getRepository().findById(schoolId)
                .map(school -> ResponseEntity.ok().body(school))
                .orElse(ResponseEntity.notFound().build());
    }

    @PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE)
    @Operation(summary = "Add new schools")
    default ResponseEntity<List<Scholen>> create(@RequestBody List<Scholen> entities) {
        List<Scholen> result = getRepository().saveAll(entities);
        return ResponseEntity.ok().body(result);
    }

    @PutMapping(consumes = MediaType.APPLICATION_JSON_VALUE)
    @Operation(summary = "Update a school, or add it when its ID is new")
    default ResponseEntity<Scholen> update(@RequestBody Scholen entity) {
        return ResponseEntity.ok().body(getRepository().save(entity));
    }

}
```

The VWO's interface also has `@NotNull` on the request bodies. Without
validation switched on for the controller (chapter 13), that annotation
is not checked, so it is left out here.

### The v1 controller

`src/main/java/be/techolympiad/common/restAPI/controllers/v1/ScholenController.java`:

```java
package be.techolympiad.common.restAPI.controllers.v1;

import be.techolympiad.common.restAPI.controllers.SchoolController;
import be.techolympiad.common.restAPI.repositories.ScholenRepository;
import io.swagger.v3.oas.annotations.tags.Tag;
import lombok.Getter;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.http.MediaType;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping(path = V1Config.BASE_URL + "/school", produces = MediaType.APPLICATION_JSON_VALUE)
@Tag(name = "schools-controller")
public class ScholenController implements SchoolController {
```

`V1Config.BASE_URL` is package-private, which is why every v1 controller
lives in the `v1` package. The VWO's version maps a second path,
`V1Config.OLD_BASE_URL + "/school"` (`/restapi/school`), a legacy alias
TechOlympiad does not have.

<div class="callout-label">When it breaks</div>

- **A 404 for every school URL, and no `schools-controller` in Swagger**: the controller is not scanned. Check that it is in a package under `be.techolympiad.common` and has `@RestController`.
- **`No qualifying bean of type 'be.techolympiad.common.restAPI.repositories.ScholenRepository'`**: `ScholenRepositoryImpl` lacks `@Repository`, or imports Spring Data's `Repository` instead of `org.springframework.stereotype.Repository`.
- **`ConflictingBeanDefinitionException`**: two scanned classes with the same simple name, often a leftover copy. Rename one, or give it an explicit name (`@RestController("scholenController.v1")`).
- **`415 Unsupported Media Type`** on `POST` or `PUT`: the request lacks `Content-Type: application/json`.
- **`400 Bad Request` with `Cannot deserialize value of type java.util.ArrayList`**: the `POST` body is a single object; it must be an array.
- **`500` with `Duplicate entry ... for key 'PRIMARY'`** in the log: a `POST` with an id that exists. Use `PUT` to change a school.
- **The response is `{}` or misses fields**: Lombok's getters are missing (see chapter 9), so Jackson finds no properties.

</div>

### Quiz

<div class="quiz" data-quiz>
<p class="quiz-q"><code>ScholenRepository</code> extends Spring Data's <code>Repository</code>. Who implements <code>findAll()</code> at runtime?</p>
<ol class="quiz-options">
<li>Spring Data, which generates a query from the method name<p class="quiz-whynot">Spring Data's repository support never runs here: Boot only enables it with a <code>DataSource</code> bean, and <code>@NoRepositoryBean</code> forbids it anyway.</p></li>
<li data-correct><code>ScholenRepositoryImpl</code>, written by hand, which delegates to <code>ScholenDao</code><p class="quiz-why">It is a plain <code>@Repository</code> bean found by component scanning, and the only implementation of the interface.</p></li>
<li>Hibernate, because <code>Scholen</code> is an entity<p class="quiz-whynot">Hibernate implements no Spring interfaces. It runs the HQL that <code>ScholenDaoImpl</code> sends.</p></li>
</ol>
<p class="quiz-explain">The VWO uses Spring Data's interface and its method names as a convention only. The behaviour is all in hand-written code, including the VWO's <code>saveAll</code> that returns <code>null</code>.</p>
</div>

<div class="quiz" data-quiz>
<p class="quiz-q">The class <code>ScholenController</code> contains no <code>@GetMapping</code>. Why does <code>GET /api/v1/school</code> work?</p>
<ol class="quiz-options">
<li>Spring generates CRUD endpoints for every <code>@RestController</code><p class="quiz-whynot">Spring MVC generates nothing; every endpoint is a method someone wrote.</p></li>
<li data-correct>The class inherits the <code>default</code> method <code>findAll()</code> from <code>SchoolController</code>, and Spring MVC reads mapping annotations on inherited interface methods<p class="quiz-why">The mapping on the interface method combines with the class's <code>@RequestMapping</code> path.</p></li>
<li>springdoc registers the endpoints it documents<p class="quiz-whynot">springdoc only reads the mappings Spring MVC already has.</p></li>
</ol>
<p class="quiz-explain">This is what lets a <code>v2</code> controller reuse every endpoint by implementing the same interface under another base path.</p>
</div>

<div class="quiz" data-quiz>
<p class="quiz-q">You <code>PUT</code> a school with id 7, which does not exist. What happens?</p>
<ol class="quiz-options">
<li>404, because there is nothing to update<p class="quiz-whynot">The endpoint never checks for existence; it calls <code>saveOrUpdate</code>.</p></li>
<li>500, because Hibernate's <code>UPDATE</code> affects no rows<p class="quiz-whynot">Hibernate does not send an <code>UPDATE</code> blindly: with an assigned id it selects the row first.</p></li>
<li data-correct>The school is inserted: Hibernate selects by id, finds nothing, and sends an <code>INSERT</code><p class="quiz-why"><code>saveOrUpdate</code> on an entity whose id is assigned by the caller checks the database to choose between insert and update.</p></li>
</ol>
<p class="quiz-explain">Our <code>PUT</code> is an upsert, like the VWO's. Chapter 13 compares this with <code>save</code>, <code>persist</code> and <code>merge</code>.</p>
</div>

### Flashcards

<div class="flashcards" data-flashcards data-front-label="Term" data-back-label="Meaning">
<div class="card"><div class="front"><code>Repository&lt;T, ID&gt;</code></div><div class="back">Spring Data's empty root interface. Normally Spring generates an implementation; in the VWO it is only a marker with a hand-written implementation.</div></div>
<div class="card"><div class="front"><code>@NoRepositoryBean</code></div><div class="back">Tells Spring Data never to generate an implementation for this interface.</div></div>
<div class="card"><div class="front"><code>default</code> method</div><div class="back">An interface method with a body. Implementing classes inherit it as a normal member, so Spring MVC can use it as a handler.</div></div>
<div class="card"><div class="front"><code>@Getter(onMethod_ = {@Override})</code></div><div class="back">Lombok getter with <code>@Override</code> on the generated method, here implementing <code>getRepository()</code>.</div></div>
<div class="card"><div class="front"><code>ResponseEntity</code></div><div class="back">Status, headers and body of a response. <code>ok().body(x)</code>, <code>notFound().build()</code>. Like <code>ActionResult&lt;T&gt;</code>.</div></div>
<div class="card"><div class="front"><code>Optional.map(...).orElse(...)</code></div><div class="back">Transform the value if present, otherwise use the fallback. Turns "found or not" into one expression.</div></div>
<div class="card"><div class="front">Default bean name</div><div class="back">Simple class name, first letter lowercase: <code>scholenController</code>. The package does not count, so equal class names clash.</div></div>
<div class="card"><div class="front">Constructor injection</div><div class="back">Dependencies as constructor parameters into <code>final</code> fields. <code>@Autowired</code> is optional for a single constructor.</div></div>
</div>

<summary>Self-check: why does the interface declare <code>getRepository()</code> instead of using a field?</summary>
<div class="ans">
Interfaces cannot have instance fields, and a default method can only call other methods of the interface. The abstract getter is the interface's way of asking each implementing controller for its repository; Lombok generates the implementation from the controller's field.
